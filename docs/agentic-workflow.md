# 旅游攻略 Agentic Workflow

## 当前待办

- [ ] Prompt 理解层：把用户自然语言解析成目的地、天数、时间、出发地、偏好、节奏。
- [ ] 搜索计划层：根据解析结果生成多轮搜索词，优先小红书/Rednote。
- [ ] 采集层：每个攻略维度采集 6 篇 Rednote 详情 + 4 个网页，默认低频慢速。
- [ ] 省 token 抽取层：不要把小红书全文直接丢给模型，先本地抽取结构化信息。
- [ ] 质量门槛：只有正文长度足够、包含地点/路线/餐厅/交通信息的笔记才进入总结。
- [ ] 聚类层：统计高频景点、路线、区域、餐厅、避坑。
- [ ] 攻略生成层：用便宜模型基于结构化摘要写攻略，而不是基于原始全文写。
- [ ] 本地调试可视化：产品运行时默认打开可见 Chromium 窗口，用户可以直接看到 Playwright 浏览过程。

## 1. 用户 Prompt 理解

输入例子：

```text
端午节，济州岛，3天，生成攻略
济州岛2天攻略
10月国庆去意大利和法国，想看天才女友巡礼
```

Agent 第一反应不应该是弹表单，而是先理解语义。

真实用户搜索路径：

```text
城市 + 天数 + 经典路线
→ 看几篇整体攻略
→ 看地图大概分布
→ 先列 must-go 和备选点
→ 找路线周边吃的
→ 根据兴趣、同行 must-go、图片种草程度做取舍
```

另一个常见路径：

```text
地点 + 想干的事
→ 如果想干的事还不清楚，就直接搜旅游攻略
→ 先看图片，图片好玩才看文字
→ 从整体攻略里选出想玩的
→ 再对想玩的地点/活动细搜
```

因此 Prompt 理解层不仅要抽显式信息，也要识别用户在隐含地做哪类旅行决策。

需要抽取：

- `destination`：目的地，例如济州岛
- `days`：天数，例如 2 天
- `date_range`：具体日期或节假日，例如端午节、国庆
- `departure`：出发地，没有就留空
- `people`：情侣、亲子、朋友、独旅等，没有就默认普通成人
- `pace`：特种兵、普通、休闲，没有就默认普通
- `preferences`：美食、拍照、海边、购物、亲子、巡礼等
- `must_include`：用户明确要看的内容
- `avoid`：用户明确不想去的内容
- `trip_initiator`：这趟旅行是谁发起的。自己发起时更偏个人兴趣；共同决定时要合并多人 must-go
- `decision_mode`：经典路线优先 / 兴趣优先 / 图片种草优先 / 多人折中 / 特种兵效率优先
- `map_planning_needed`：是否需要按地图分布聚类，默认 true
- `candidate_policy`：输出 must-go 和备选点，不要只给唯一行程
- `visual_pull`：图片是否影响决策。默认小红书图片对种草有影响
- `interest_discovery_mode`：用户是否一开始不知道想玩什么，需要先从整体攻略里发现兴趣点
- `image_first_mode`：是否先用图片吸引力筛选笔记，再读正文。默认对小红书成立

隐含默认值：

- 用户只说「城市 + 天数」时，先按「经典路线 + 高频景点 + 地图顺路」理解。
- 用户提到兴趣关键词时，搜索计划要加入兴趣词，例如书店、咖啡、夜樱、动物园、巡礼。
- 用户没有兴趣关键词时，不要强行追问；先搜整体攻略，从高频地点、图片吸引力和活动类型里反推候选兴趣。
- 用户说「一起去」「我们」「朋友/对象」时，要预留多人 must-go 合并逻辑。
- 用户没有给偏好时，不要先问一堆问题，先从整体攻略里提取高频路线，再最后补问偏好。
- 输出不只是一张日程表，还要有「要去地点」「备选地点」「路线周边吃的」。

如果信息不足：

- 缺目的地：必须追问
- 缺天数：可以先按 3 天默认，也可以轻量追问
- 缺日期：不阻塞攻略生成，只在季节/天气/节假日部分提示待确认
- 缺偏好：最后再问，不要一开始打断

## 2. 搜索计划生成

输入：

```json
{
  "destination": "济州岛",
  "days": 2,
  "pace": "普通",
  "preferences": []
}
```

输出搜索计划：

```json
{
  "xiaohongshu": [
    "济州岛2天攻略",
    "济州岛两天一夜攻略",
    "济州岛周末攻略",
    "济州岛2天路线",
    "济州岛东线西线攻略",
    "济州岛避雷"
  ],
  "web": [
    "济州岛 2天 行程 交通",
    "site:mafengwo.cn 济州岛 2天 攻略",
    "site:qyer.com 济州岛 2天 攻略",
    "site:lonelyplanet.com Jeju travel guide itinerary",
    "济州岛 官方 交通 景点 开放时间",
    "Jeju 2 day itinerary attractions transport"
  ]
}
```

规则：

- 首轮搜索模拟用户习惯：`城市 + 天数 + 经典路线`。
- 基础格式：`目的地 + 自由行/自驾/亲子 + 天数 + 攻略`，例如 `三亚自由行 5天攻略 2026`。
- 如果用户只有地点，没有明确想干什么，先搜 `地点 + 旅游攻略`，不要直接追问。
- 如果用户给了想干的事，搜 `地点 + 想干的事`，例如 `首尔 买手店`、`南京 夜樱`、`济州岛 咖啡厅`。
- 第一轮采集后，从攻略里抽出候选兴趣点，再生成第二轮细搜词。
- 第二轮搜索围绕地图和区域：`城市 + 区域/东线/西线/市区 + 路线`。
- 第三轮搜索围绕兴趣：把用户兴趣词加入查询，例如 `南京 先锋书店 攻略`、`南京 夜樱 小红书`。
- 第四轮搜索围绕吃：`路线周边吃的`、`区域 美食`、`景点附近 餐厅`。
- 小红书/Rednote 先搜用户原话，再搜同义词。
- 天数类词要扩展：`2天`、`两天一夜`、`周末`、`48h`。
- 行程类词要扩展：`路线`、`东线`、`西线`、`牛岛`、`城山` 等由首轮资料再补。
- 细分场景要扩展：`美食地图`、`避雷指南`、`小众景点`、`住宿推荐`、`交通攻略`。
- 时间限定要扩展：如果用户给了年份/月度，搜索词带上 `2026`、`2026年6月`、`近期`、`最新`。
- 人群限定要扩展：`带父母游`、`亲子游`、`大学生穷游`、`情侣约会`、`独旅`、`带老人`。
- 避坑类单独搜：`避雷`、`踩雷`、`后悔`、`不推荐`。
- 普通网页补充源固定包含：马蜂窝、穷游、Lonely Planet。
- 中文攻略优先看马蜂窝/穷游的路线和游记，英文目的地信息优先看 Lonely Planet。

搜索计划要产出 4 类结果：

```json
{
  "classicRouteQueries": [],
  "interestDiscoveryQueries": [],
  "interestMatchQueries": [],
  "mapClusterQueries": [],
  "foodNearbyQueries": [],
  "sceneQueries": [],
  "timeSensitiveQueries": [],
  "travelerTypeQueries": []
}
```

## 3. 资料采集

当前主线：

```text
Playwright
→ Rednote 登录态
→ 搜索页
→ search/notes 接口拿卡片和 xsecToken
→ 详情页
→ feed 接口或 DOM 拿正文
```

默认限制：

- 每个维度最多读 6 篇 Rednote/小红书详情。
- 每个维度补充 4 个网页资料。
- 每篇详情停留 12-22 秒。
- 篇与篇之间停 5-12 秒。
- 遇到登录、安全提示、验证码时停止，不继续刷。

成功标准：

- `authStatus.loggedIn = true`
- `hasXsecToken = true`
- `text` 不只是标题，正文长度建议 > 120 字
- 每个维度至少 3 篇有效详情，最好 6 篇 Rednote + 4 个网页

本地调试可视化要求：

- 本地产品默认 `headless=false`，直接打开 Chromium 窗口。
- 用户可以看到 Playwright 搜索、点击、阅读详情的全过程。
- 暂不在产品右侧嵌入 live browser 面板，避免 UI 复杂化。

## 4. 省 Token 抽取层

目标：把每篇长笔记压缩成结构化摘要，再交给模型。

不要直接把原始全文丢给模型。先用本地规则抽：

```json
{
  "title": "济州岛周末特种兵两天往返攻略",
  "url": "https://www.rednote.com/explore/...",
  "author": "作者",
  "places": ["牛岛", "城山日出峰", "月汀里", "保健路"],
  "restaurants": ["黄金鳗鱼", "黑猪肉店"],
  "areas": ["东线", "济州市区", "涯月邑"],
  "routes": [
    {
      "day": "D1",
      "items": ["牛岛", "城山日出峰", "月汀里"]
    }
  ],
  "transport": ["打车", "公交600路", "包车", "一日团"],
  "tips": ["住宿建议靠近机场/保健路", "牛岛适合东线一起玩"],
  "costs": ["打车约15000韩元"],
  "timeHints": ["周五晚到", "周日晚返程"],
  "evidenceText": ["保留 3-5 条最关键原文片段"]
}
```

本地规则优先抽：

- D1/D2/DAY 1/Day1/第一天/第二天
- 箭头路线：`A → B → C`、`A➡️B➡️C`
- 地名后缀：峰、海水浴场、咖啡、市场、免税店、路、邑、里、机场
- 交通词：公交、打车、包车、自驾、机场、航班、地铁、步行
- 金额词：韩元、人民币、人均、门票、打车费
- 避坑词：不要、不建议、排队、预约、关门、坑、踩雷、注意

模型只吃：

- 每篇结构化摘要
- 高频地点列表
- 关键原文证据片段
- 用户原始需求

## 5. 聚类和判断

把多篇摘要合并：

- 高频地点：出现 3 次以上优先进入候选清单。
- 高频路线：按出现顺序聚类，例如 `牛岛 + 城山 + 月汀里`。
- 地图聚类：把地点按区域/相邻关系分成同一天，不要跨区域来回跑。
- 兴趣匹配：高频但不匹配用户兴趣的点降级为备选；低频但强匹配兴趣的点保留。
- 多人 must-go：共同旅行时，每个人的 must-go 都要尽量安排进顺路路线。
- 图片种草：图片吸引力高但信息少的点进入备选，后续用地图/评论验证。
- 先图后文：图片强吸引但正文弱的笔记，只作为灵感；正文有路线/交通/费用的笔记，作为攻略证据。
- 兴趣发现：从整体攻略里归纳活动类型，例如海边、咖啡、书店、夜景、徒步、购物，再决定二次搜索关键词。
- 高频住宿区域：机场、市区、保健路、涯月邑等。
- 争议地点：同时出现推荐和避雷，标注为“有争议”。
- 交通判断：如果多篇都说打车/包车，攻略里不要强推公交。

输出中间结构：

```json
{
  "topPlaces": [],
  "topRoutes": [],
  "mustGo": [],
  "backupPlaces": [],
  "mapClusters": [],
  "food": [],
  "transport": [],
  "pitfalls": [],
  "sourceEvidence": []
}
```

## 6. 攻略生成

模型输入应该是结构化中间结果，而不是原始网页全文。

生成顺序：

1. P0 生存指南
2. 前期准备
3. 高频景点和路线判断
4. 分日行程
5. 餐厅/咖啡
6. 交通方案
7. 避坑合集
8. 来源链接

生成时必须标注：

- 哪些是多篇笔记共同出现
- 哪些是单篇提到，需要二次确认
- 哪些是官方信息待确认

## 7. 下一步实现顺序

1. 实现 `extractEvidence` 本地规则版。
2. 把 Rednote 采集结果接到 `extractEvidence`。
3. 先不用模型，打印结构化摘要，验证地点/路线是否抽对。
4. 再接 DeepSeek V4 Flash 写最终攻略。
5. UI 上显示进度：理解需求、搜索计划、采集、抽取、生成。
